线下生产进度总表 → 系统化 落地规划方案

虹越智造平台 · 安徽虹越（注塑/吹塑）· 核心目标：并行过渡、降低使用者习惯变更、提升便捷性
依据：2026生产进度总表-2026-09-03.xlsx（11 sheet / 2161 行） 策略：导出同格式 + 车间逐步切换 编制日期：2026-09-07

摘要 · 三句话结论

  1. 不要一次性废掉 Excel。采用「并行过渡」：系统成为唯一数据源，但每天能一键导出与线下完全同格式的总表，业务端拿到的还是熟悉的表格——这样业务端零学习成本。
  2. 第一期绝不碰车间。先做「Excel 导入建档 + 导出同格式 + 只读进度总表页」，让计划员/业务员先感受到「不用手工算、不用每月复制 sheet」，建立信任后再切换报工。
  3. 复现习惯，而不是推翻习惯。「报工月历页」保留线下「一行一工单 × 一列一天」的填写手势，点格子填数即可；区别只是填完后三道工序进度与汇总自动更新，并且把线下缺失的喷漆每日报工补上。

1.4 数据质量隐患（导入前必须先处理）

已发现的问题

  • 147 个工单号重复：系整行复制粘贴导致（产品、订单号、数量、完成数完全相同），非「一工单多产品」
  • 工单号类型混用：int 1399 个 + 文本 446 个
  • #DIV/0! 满表：箱数/托数/体积等除零错误
  • 交期列混入字符串类型值

系统侧天然免疫

  • task_no 由 TSK-{order_no}-{seq} 生成，唯一约束根除重复
  • 工单号统一按字符串存储，保留原「入表序号」溯源
  • 除零场景由服务端计算，输出 — 而非错误值
  • 导入时逐行校验，错误行反馈行号、不阻塞合法行

三、核心产品设计：复现习惯 + 顺手减负

C1 · 「生产进度总表」页（1:1 复现主表观感）

做法：把线下主表原样搬进系统——一行一个工单，列组保持「标识 → 业务员 → 客人订单号 → 订单数量 → 交期 → 三道工序组 → 装箱组」，字段名与顺序都和 Excel 一致。

比线下便捷的地方

  • 需要班次自动算：ceil(未完成 ÷ 班次产能)，彻底告别 #DIV/0!
  • 实时汇总：报工落库即更新，不再是「等统计员月底填完」的快照
  • 红灯提醒：交期逾期、未完成 > 0 自动高亮（复用既有 RedLightService）
  • 重复根除：task_no 唯一约束，不会再出现 147 个重复工单号
  • 点击钻取：点工单号看该工单三道工序的明细与报工流水

建议路径：frontend/src/views/production/ProductionProgressView.vue（新建）+ 后端 GET /production/progress-grid

C2 · 「报工月历」页（保留填写手势，一次填报全联动）★ 降低习惯变更的关键

做法：完整复现线下月历 sheet 的填写手势——一行一个工单、一列一天（1~31 号），找到格子填数。视觉和操作与 Excel 几乎一致，统计员无需重新学习。

工单号码产品名称订单数量 1号2号3号…30号31号月完成总数多做的未完成
T-2026-018616寸艾德勒盆黑色192———…——19200
T-2026-04508寸马洛里盆棕色330—120210…——33000

与线下的差别（都是减负）

  • 点格即报工：点任意日期格 → 弹窗填合格/次品/班次/备注 → 走既有 POST /api/reports，无需手算累计
  • 填一次，全联动：三道工序进度、主表已完成/未完成/需要班次、汇总视图同步更新（线下要填两张表 + 改主表）
  • 喷漆纳入：月历顶部按 op_type 切换（成型 / 喷漆 / 包装），补上线下缺失的喷漆日报工
  • 不必每月复制 sheet：切月份即可，历史数据永久可查
  • 超产自动标识：超过订单量自动计入「多做的产品数量」并留痕

建议路径：frontend/src/components/production/ReportCalendar.vue（新建）+ 后端 GET /reports/month-calendar?year=&month=&op_type=

C3 · 「业务端汇总视图」（替代 6 张透视表）

做法：把线下 6 张离线透视表合并成一个实时汇总页，筛选器与线下保持一致（交期多项、成型班次），行维度可切换。

  • 维度切换：按产品 / 交期 / 业务员 / 客户 聚合（线下缺业务员维度，G1 补上后即可支持）
  • 指标对齐：订单数量-产品数、成型未完成、喷漆未完成、包装未完成、成型需要班次
  • 实时性：不再需要手动刷新透视表；管理层随时看当前负荷

建议路径：frontend/src/views/production/ProgressSummaryView.vue + GET /production/summary?dim=product|due|salesperson|customer

C4 · Excel 导出（同格式，业务端「熟悉的味道」）★ 并行过渡的支柱

做法：一键导出三个 sheet，列名与顺序对齐线下，业务端拿到手还是原来那张表。

导出 Sheet对齐线下说明
订单明细2026订单明细47 列结构，含三工序组与装箱组；除零场景输出 —
X月成型当日完成 / X月包装当日完成 / X月喷漆当日完成8月成型/包装当日完成1~31 号日期列 + 月完成总数 / 多做的 / 未完成 / 产能
汇总6 张透视表按产品/交期/业务员聚合未完成量与需要班次
技术可行性已确认：maatwebsite/excel ^4.0 已在 hongyue/composer.json 的 require 中（目前仅用于导入）， 新建 app/Modules/Order/Exports/ 即可实现导出，无需新增依赖。

C5 · Excel 导入（每行一工单 + 历史建档）

做法：改造现有导入，新增工单级模式：每行 → 独立 Order + OrderLine + ProdTask，与线下「每行一个工单」语义一致。

  • 历史建档：一次性把 2161 行历史工单导入系统，作为数据底座
  • 过渡期兼容：如果个别工序仍想先用 Excel 记，可导入后由系统汇总
  • 容错：工单号重复、产品不存在等错误行反馈具体行号，不阻塞合法行
  • 字段映射：业务员、客人订单号、工厂款号、装柜日期、装箱组一并导入（G1/G2 支撑）

建议路径：改造 Order/Imports/OrdersImport.php + ExcelImportService.php，新增 mode=workorder

C6 · 交期变更（必填理由 + 自动留痕）

做法：改交期不再只是改个日期——必须选择变更理由，系统自动记录「旧值 → 新值 → 谁改的 → 何时改的」。

  • 理由枚举沿用线下：生产主任变更 / 业务同意晚点 / 模具保养维修 / 计划调整（临时加单）/ 其他
  • 专用表：delivery_change_logs(order_id, old_due, new_due, reason, operator_id, created_at)
  • 可追溯：替代线下「交期变更记录」sheet，且无法被误删或漏记

四、分阶段路线图

第 1 期

零阻力 · 立刻有感知

目标：业务端先熟悉系统出的数据，车间完全不改
  • G1 业务员字段（+迁移）
  • G4 工单级导入（历史建档）
  • G5 主表/汇总 Excel 导出
  • G11 只读「生产进度总表」页
习惯变化：计划员停止维护线下主表（改用系统导出件）；业务员开始看系统导出的表。车间零变化。
验收：导出表字段与线下主表一致；导入每行生成独立工单；重复工单号被拦截。
第 2 期

减负 · 统计员先受益

目标：统计员不再手填月历、不再维护公式
  • G6 报工月历页（点格填报）
  • G7 喷漆纳入每日报工
  • G8 班次产能与「需要班次」
  • 移动端扫码报工沿用既有
习惯变化：从「Excel 里翻行填日期列」→「系统月历页点格填数」，手势基本一致；喷漆首次拥有日报工。
验收：填一次三工序联动更新；需要班次数值与线下口径误差 < 1 班次。
依赖：一期已完成数据建档。
第 3 期

自助 · 业务端受益

目标：业务员自助查，管理层弃用离线透视表
  • G9 业务端透视汇总页
  • G3 交期变更留痕（理由必填）
  • G2 装箱/装柜字段补全
  • G10 超产留痕
习惯变化：业务员不再打电话问进度；改交期必须选理由（一次性适应）。
验收：汇总页维度聚合准确；交期变更 100% 留痕可追溯。
第 4 期

双轨合并

目标：线下 Excel 停用，全量系统报工
  • 导出能力保留作审计用途
  • 数据质量看板
  • K3 拉单复用导入通道
习惯变化：线下表停更，车间全部走系统/移动端报工。
验收：连续 2 周系统数据与车间实况一致，线下表停止更新。
为什么第 1 期最重要：它不要求任何人改变操作习惯，却能让所有人第一次看到「系统产出的数据」。 信任建立之后，第 2 期让车间改用月历页的阻力会小得多——因为那时他们已经确认「系统算出来的数和我们记的一样」。

五、关键风险与对策

风险影响对策
产能口径换算误差
（线下"班次产能" vs 系统"件/小时"）		 「需要班次」与线下算的不一致 → 计划员不信任系统 派生：班次产能 = capacity_per_hour × 班次小时（已核实：两班制单班 12h，白班 9h）。上线前用线下实际产能（成型 800/700/2500/3200）反算校验；过渡期双口径并列显示，确认一致后再单轨
数据质量
（147 重复工单号、int/str 混用、#DIV/0!）		 导入后数据混乱、统计翻倍 导入前清洗：按「工单号+产品+订单号+数量」去重；工单号统一转字符串；原「入表序号」保留溯源。系统侧 task_no 唯一约束兜底
双轨期数据不一致 Excel 与系统两套数，谁为准？ 明确系统为唯一真源，导出件仅供业务端查看（标注导出时间戳）；日结时统计员核对差异，用冲减（sign=-1 + remark）修正，已有机制支持
车间抵触 一线不用，系统沦为摆设 第 1 期完全不动车间；第 2 期月历页交互贴近线下「点格填数」，学习成本 ≈ 0；同时提供移动端扫码报工降低门槛；先让统计员（受益最大的人）成为推动者
喷漆日报工工作量新增 喷漆班组觉得"多了一份活" 强调这是补上线下遗漏（原来也要报，只是没表、更混乱）；提供移动端快速报工；可先由班组长代报过渡
超产/错误报工 数据失真 既有超产上限校验 qty×(1+over_report_pct%) + 5 分钟防重窗口 + 冲减留痕（sign=-1+remark 必填）+ 弱网离线补传

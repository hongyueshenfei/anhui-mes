校验规则（PUT route-ops）

  • 状态门禁：仅 route_confirm / pending 可编辑，已排产及之后一律 422
  • 逐工序必填：op_name、workshop_id；成型工序（注塑/吹塑）必须选机台且 type 匹配；人工线工序必须选产线
  • seq 强制重排：无论提交顺序如何，落库一律 1..n
  • 空工序拦截：ops: [] 且未带 restore_standard → 422（防止用户把工序删空还能保存）

需求量算式

七、过程中修掉的两个缺陷

缺陷 1 · 前后端语义对不上（双方单测都覆盖不到）

现象：前端「恢复标准路线」提交 ops: [] 表示清空定制；后端 OrderService 把空 ops 判为非法输入直接 422 → 该功能点了必然报错。

修法：引入显式布尔 restore_standard 区分「清除定制」与「非法空工序」，不放松空工序校验。

第二层（更隐蔽）：控制器 'tasks.*.ops' => 'required|array|min:1' 会在 validate 层就拦掉 ops: []，service 里的分支根本走不到 —— 必须同步改成 required_unless:tasks.*.restore_standard,true。只在 service 层改是不够的。

缺陷 2 · 演示数据遗留值导致领料清单数值失真

BOM 1/2 的 RAW-PP-001 是历史遗留值 1.02 kg/件，5000 只杯子算出 5202 公斤 PP，明显不合理。因 seeder 幂等跳过已有行而残留（全新安装走的是新口径 0.022）。

处理：已手动将开发库该值修正为 0.0220 kg/件 → 5000 只 = 112.2 kg，与新口径一致。
